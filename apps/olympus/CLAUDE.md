# CLAUDE.md

Olympus Studio: a JUCE standalone app (macOS, builds on Linux for CI) that holds a timeline of clips on tracks (with a tempo map, markers, a loop and undo), a chain of plugins on each track, and writes the stems out; plus an MCP server over the same session so an agent can place the chains. See [README.md](README.md) for what it does, and [../../CLAUDE.md](../../CLAUDE.md) (`## Layout and dependency direction`) for the runtime-only plugin hosting, `suiteNames()`, and `scanSuiteOnly` rules.

## Build and verify

Build, test and snapshot commands live in [README.md](README.md) (`## Build & develop`); shared defaults and `scripts/build.sh` live in [../../CLAUDE.md](../../CLAUDE.md) (`## Building and checking`, `## Module conventions & defaults`).

- `OlympusMcp` is the MCP server target; `OLYMPUS_PLUGIN_DIR=$PWD/plugins/hermes/build scripts/build.sh olympus tests` runs the real plugin hosting check (run it by hand after touching `Catalog.h`).
- `OlympusTests` and `OlympusUiCheck` need no built plugin and no audio device: plugins are `test::GainPlugin` (`Tests/TestPlugin.h`, a gain with two presets and an optional latency).
- `UiCheck` runs headless with no display: it replaces `makeEditorWindow` so no native window is opened (a native window under a bare X server aborts the process).
- There is no listening test. Real-time playback, the audio device and the plugin editors in their own windows are checked by a person on the Mac; say so in the commit.

## Invariants

- **One Session, three users.** The window, the server and the tests all call `Session` (timeline edits through `Editor`, below); none keeps a copy of its state. Anything that changes tracks, clips or chains holds `Session::lock`; the audio callback only *tries* it (silence for that block if it cannot).
- **All tracks render together, block by block**, never one after another: Hestia's instances read each other through a bus in the plugin binary, so a track rendered alone would hear no neighbours. Keep it so.
- **A stem is aligned with its audio**: the chain's latency is taken off the front (and the run is longer by the longest latency); the real-time path delays the other tracks instead (`Track::delaySamples`). Test [4] and [5] pin both.
- **Stems are 32-bit float by default**, so they cannot clip and can be edited later; the mix is the sum of the written stems; a muted track (or one not soloed while another is) writes no stem. `RenderOptions::writeStems` off writes only `mix.wav`, which runs the tracks together exactly as a full render does (same bytes).
- **The message thread never waits for `Session::lock` while a render runs. Paint and `notes()` read the monitor latency with a try-lock (`monitorLatencyMs`, the value kept while busy), never `Session::monitorLatency`.** `renderStems` holds the lock for its whole run and sets `Session::renderBusy` (`renderRunning()`). `ArrangeView::snapshot` waits for the lock normally (the audio thread holds it for a moment each block) and returns its last model only when a render runs; the timer skips the latency update and the plugin-state check while a render runs. Any new timer or paint path follows the same rule (test [21]). A cancelled render closes and deletes the files of its own run and reports nothing (`RenderResult::stopped`); a render that fails after its files were made deletes them too (`discardRun`, test [20] proves the stems existed at the cancel). A render overwrites a same-named stem of an earlier render in that folder as soon as it starts (`makeWriter` deletes it first).
- **A project never loses what it cannot use.** A missing plugin stays as a slot with its saved state (`Slot::savedState`), a missing audio file keeps the track and its path; both are `warnings`, never errors. A project from a newer version is refused.
- **The project format is versioned** (`version` on `OlympusProject`); add attributes, never change what one means, and ignore what is unknown, as Orpheus' file does.
- **The server writes only what it is told to** (a project path, a render folder) and prints nothing but protocol on stdout. Every tool failure is an `isError` result with a reason an agent can act on; keep the 48 tools in `tools()` and in README in step.
- **The monitor chain is playback only, never in a render, not in the project, saved in `monitor.xml`**: `Session::processMonitor` runs after `processBlock` on the audio callback's playback block and nowhere else; `renderStems` and `processBlock` never touch it (test [31]), and it is not an undo step.
- **MIDI input has two FIFOs, and only the piano roll's preview shares the message thread's.** `Session::liveMidiFifo` is the piano roll's preview (one producer, the message thread). `Session::inputMidiFifo` is the hardware: `handleIncomingMidiMessage` runs on each device's MIDI thread, several at once, so it pushes under `inputMidiLock` (a `juce::SpinLock`, held by the producers only). The audio thread is the single consumer and takes no lock. Both are drained in `processBlock` in both passes; the hardware events are drained into their own scratch (`inputMidiScratch`) so the take can capture them alone, and then appended to `liveMidiScratch`. A timed event (`timeMs`, from `juce::Time::getMillisecondCounterHiRes()`) is placed by its age in the block, as `juce::MidiMessageCollector` does; a preview event has no time.
- **A take captures hardware notes only, and before the try-lock.** While `Session::midiRecorder` records and the transport rolls, `captureMidiInput` pushes the note-ons, note-offs, sustain (CC 64) and pitch bends of `inputMidiScratch` at `start + offset`. It runs before the try-lock, so a snapshot-fallback block records too. Nothing is captured during the count-in (the stopped pass). The ring (32768 events, `MidiRecorder`) is preallocated; a full ring counts `lostEvents()`, reported like an audio take's loss. The MIDI clips (`buildRecordedMidi`, `finishMidiRecording`) pair the events by channel and pitch, end a note still held at the stop at the transport's position, and move each note earlier by the playback latency (`takeMidiLatency`: output latency, `extraLatencySamples`, monitor and the longest chain; the input latency is left out, because the note is placed where it was heard). A note whose shifted start is before 0 is dropped (the rest keeps its time); a note whose shifted start lies outside a punch range is dropped and one that runs past the punch-out is cut at its end; the sustain pedal (CC 64) holds a released note until the pedal is up (or the same key is played again). They are one undo step with the audio takes (`finishRecordingTakes` holds one `Editor::Gesture` over both), one clip per armed MIDI track as it was armed at REC (`takeMidiTracks`). The clip starts at the bar before the first note's bar (0 at the earliest) and ends at the bar after the last note-off's bar, and the notes' beats count from its start.
- **A MIDI-only REC is valid: no file, but a take.** `beginRecording` starts `Recorder::start` with the audio takes alone (possibly none; no folder is made for none) and starts the MIDI recorder when a MIDI track is armed. `isRecording()` is then true, so the window's take logic (seek refused, the loop not wrapping, `takeStart` latched in `push`) works as for an audio take. "No track is armed" is said only when there is neither an audio take nor an armed MIDI track.
- **An armed MIDI track plays its live input while the transport is stopped, and only its live input.** The stopped pass (`processMonitoringOnly`) is run for it (`anyMonitoring` is true while any MIDI track is armed, by `refreshMonitoringLocked`), and `hasSource` takes it, so `runChain` gives its BasicSynth or MIDI plugin the live events only; its clip MIDI and clip audio are not played while stopped (`rolling` false), and `monitoringInput` still says no for a MIDI track. The window's `handleIncomingMidiMessage` is the only producer; the checks call it with a null input. With no monitoring track and no armed MIDI track the stopped transport does not run the pass, so `Session::dropLiveMidi` takes the notes out of both FIFOs instead: they are not kept for a track armed later.
- **Recording is real-time safe, its files are written by a thread, and a take lands minus the latency**: `Recorder::push` allocates nothing, takes no lock and does no file IO (the `ThreadedWriter`s do, on a `TimeSliceThread`); `stop()` waits for a push in flight before it closes a file; `finishRecording` puts each take at `startSample - latencyCompensation`, or at 0 with the head before 0 skipped (`offset`), as one undo step. A take's disk problems are kept per take: `Recorder::Finished::lost` counts the frames the writer's FIFO refused (on the audio thread), and `failed` is set by `CheckedWriter`, which sits between the WAV writer and JUCE's `ThreadedWriter` (that one drops the result of its writes), when a write to the file fails on the writer thread. `stopRecording` reports both, and the head the opening cost: the lost samples with their length in ms (dropped frames are not written, so the take is shorter by that much and what follows the loss sits that much early; nothing is padded; with several takes that lost samples, the largest is named with its track and the others are listed); a file that failed keeps what it holds; the samples that arrived while the files opened or while a device change waited were neither written nor padded and are said with their length in ms (`DeviceCallback::deviceBlock` counts `Recorder::samplesSkippedWhileOpening()` both while the window's `recordStarting` guard is up — a guard `Recorder::start` raises itself, after it cleared the take's counters — and while `deviceStarting` is up during a running take or opening (`recorder.isRecording() || recordStarting`), while holding outputs silent until the message thread prepares the new device and ends the take). `finishRecording` skips a take it cannot place and places the rest; the first reason is reported (test [41]).
- **One audio path, the device's.** `MainComponent::DeviceCallback::deviceBlock` is what the device calls and what the checks call with their own buffers: the inputs go to `Recorder::push` first (always, so the meters work), then `Source::getNextAudioBlock` fills the outputs (it clears them first, so unused outputs are silent). `processMonitor` runs on the playback block after `processBlock`, as its invariant says. A device with no outputs plays nothing, but its transport still advances (into a scratch buffer) and its takes still get their inputs; a device that leaves one output channel null is never written through it, and the channels it does have are cleared (test [42]). `audioDeviceAboutToStart` (before the callbacks start; marshalled to the message thread if it comes from another) ends a running take, because a take cannot go on across a new rate or block size, prepares the recorder and the transport's scratch, and adopts the device's rate - while a render holds the session's lock it keeps the start instead and holds the outputs silent, and the timer lands it once the render lets go; `audioDeviceStopped` (device thread) only sets a flag that the timer reads and ends the take.
- **Takes name device inputs by their absolute number; the callback passes only the switched-on ones.** The device hands `deviceBlock` its active inputs in order, so `Recorder::prepare` maps each absolute input to its position (`position`, -1 when it is off). A take or a meter on an input that is off is silence, and REC refuses that take with the track and the input named. `inputChoices` offers only the inputs that are on.
- **A take starts where the playhead was at its first block.** `deviceBlock` reads the position before the block plays and gives it to `Recorder::push`, which latches the take's start (`takeStart`) with one compare-exchange inside the `busy` scope `stop()` waits for, so the start and its first write are one decision a stop cannot come between; `Recorder::start` clears it with the take's other counters. `stopRecording` reads `Recorder::takeStartSample()` and `samplesSkippedWhileOpening()` and places each take at `start - latency`, with the latency fixed at REC (device input + output latency + `extraLatencySamples` + `Session::monitorLatency()` + `Session::maxLatency()`, the longest track chain the tracks are delayed by); when no block ever ran, the position REC was pressed at is the start. While a take runs the loop does not wrap unless loop recording was on at REC (below), the end of the audio does not stop it, `seek` is refused (the take is one continuous recording), and a track cannot be removed.
- **Punch trims a take at the stop, needs layers, and starts two bars early.** `startRecording` with `session.punchOn` takes the range (`takePunch`, fixed at REC) and seeks to two bars before its start (at the tempo there) before `takeFrom` is read, so the take has a head to hear. The takes record all the time; `finishRecording` trims each one after its latency placement (start, offset and length move together, `[punchStart, punchEnd)`), and a take that ends before the punch-in or starts after the punch-out is not placed and is named (Tests [73], UiCheck [62]). `Editor::setPunch` refuses to turn on while the session is not layered, and `setLayered (false)` turns the punch off in the same step. The punch range is a `Session` field, saved as attributes and scaled by `adoptRate`; undo takes it with the other EditState fields.
- **Loop recording is decided at REC and fixed for the take.** `Source::loopRecording` is set in `startRecording` to the session's loop on, a loop with an end after its start, and no punch; the take's loop points are kept in `takeLoopStart` and `takeLoopEnd`, and the callback wraps at those while the take runs (the playback loop is not read then). With the loop on REC is refused without layered clips (the reason, the playhead unchanged); a playhead outside the loop is moved to its start first, and that is undone on a refusal.
- **Each pass of a loop take is a take, from `loopPasses`, and the last pass plays.** `loopPasses` (Record.h) cuts the file: pass 0 from the take's start to the loop's end (placed at `start - latency`, its head before 0 skipped as for any take), then one pass per whole loop at `loopStart`, the last one cut to what was recorded; a pass under 100 ms is dropped. `finishRecording` adds the passes in order, so each layer is above the last, and gives them one new take group (`Editor::newTakeGroup`) with `takeIndex` 0..n-1, in one undo step. A take without the loop is one clip in a group of its own.
- **The MIDI of a loop take is paired in arrival order.** With a loop, `buildRecordedMidi` takes the events as they came (the transport wraps, so their positions are not in order); a note whose off position is before its on was held across the wrap and ends at the loop's end. Without a loop the events are sorted by position as before. All passes go into one clip.
- **Comping copies a range of a take, and a take is promoted by its layer.** `Editor::compTake` makes a clip on the take's own audio from `start` to `end` (inside the take, at least 1 ms; `offset` moves with it), with the same take group and index, `comp = true`, no fades of its own and the layer above every clip on the track, in one undo step. `Editor::promoteTake` raises a take above every clip (a comp is refused: promote the take it came from). Both are undone as one step. The take group of a comp is the take's, but the take lanes do not list a comp as a lane.
- **Take lanes are the view of the takes, and a sub-lane's part that plays is lit.** `Track::showTakes` (saved; a view setting, not undone) opens one 22 px sub-lane per take clip under the track's main lane, in take order, before the automation lane; the TAKES switch is shown only for a track with a take group of two or more takes. A sub-lane shows its clip dimmed, lit where no higher unmuted clip covers it (`ArrangeView::audibleSegments`, the layers' order). A drag across a sub-lane comps that range on release (snapped when snap is on), a click on its label promotes the take. Every row height and hit test goes through `trackHeight`, `takeLanesHeight` and `autoLaneRect`, so the sub-lanes move with the rest.
- **Input monitoring is the device's input, through the track's chain, and it is never in a render.** `Session::monitoringInput` says who monitors: an armed audio track whose `monitor` is In, or Auto while a take records or the transport is stopped; a bus, a MIDI track, a frozen track or one with no input never does. `DeviceCallback::deviceBlock` hands the session the device's inputs by absolute number (`setLiveInputs`: a stack array, valid for that one block and only while a track monitors, `anyMonitoring`). `Source` sets `liveInputOffset` before each `processBlock`, so the inputs and the playhead move together (the count-in's clicks come first); `runChain` copies the inputs into the track's scratch in place of its clips, and the chain, fader and pan follow. While the transport is stopped, `Source` runs `processMonitoringOnly` (`processBlock` with `rollingPass` false: the monitoring tracks, the armed MIDI tracks' live input (F7), buses and master only; no clips, clip MIDI or metronome; the playhead held; the discontinuity state untouched) and then `processMonitor`. A render, a freeze and the snapshot fallback (`processBlockFromSnapshot`, which plays clips) never monitor (tests [74] and UiCheck [63]).
- **The count-in is click only, and holds the position.** While `Source::countInLeft` is above 0, the first samples of each block are the click (`Session::addMetronomeWith` on `countInMap`, the session's tempo reduced to the tempo at the record point) and they are not played: the position does not move and `processBlock` is not called for them. `deviceBlock` gives the recorder only the meters for those samples (`Recorder::meterOnly`), then the rest of a block with the input pointers moved past the click, so the take's first sample is the record position and the take starts at the first sample after the count-in. `startRecording` writes `countInTotal` and `countInMap` before it stores `countInLeft`, and waits for `countInReading` (the audio thread's read of the map) before it writes the map again; `stopRecording` sets `countInLeft` to 0 and a stop in the count-in places no clip (UiCheck [62]). Neither the `recordStarting` nor the `deviceStarting` guard advances the count-in.
- **Plugins are created and edited on the message thread.** The window and the server run on it. `runRenderJob` closes the tracks' plugin windows, stops the transport and calls `session.prepare(true)` on the message thread before its progress window's worker starts, and restores `session.prepare(false)` when it finishes; `OfflineScope` in `Session::renderStems` is a no-op when `session.offline` is already true.
- **A start that died is not repeated.** The monitor chain and the last project are loaded between two pedal files (`monitor-load.pedal`, `project-load.pedal`, Settings.h): a pedal found at start is removed and that load is skipped, the file is left untouched, and a note says so. `loadSkippedMonitorChain` (PLUGINS) reads the chain again with the pedal around it.
- **A plugin's latency change is followed on the window's timer.** Its listener (`LatencyWatch`, one per session, removed by each slot before its instance goes) only sets a flag; the timer calls `updateLatencies`. The MCP server has no timer and does not follow it.
- `LampButton` exists only because `shared/ui`'s look-and-feel lights every switch in one colour; if the kit grows per-button colours, use them and delete it.
- **Every timeline edit goes through `Editor`** (`Source/Edit.h`): tracks, plugins, chains, clips, track gain, pan, mute, solo and name, the master, tempo, time signature, loop, metronome, markers, snap and grid. It takes the session lock, refuses a bad argument with a reason and changes nothing, and pushes one undo step per change (structural track/plugin changes store XML snapshots and call `onBeforeStructureChange` before restoring); a `Gesture` makes a drag one step. Snap and grid are saved (and restored with structural steps) but are not undone on their own. Nothing else writes those fields: the window, the arrangement and the server all call `Editor`.
- **Polarity is at the source, before the chain, in every path.** `runChain` inverts both channels of `t.scratch` after the clips, the bus input or the instrument, and before the first chain slot (`FloatVectorOperations::negate`, no allocation). The snapshot path (`processBlockFromSnapshot`) does the same after its clip mix and before the pre-fader sends; `renderStems` and `freezeTrack` get it through `runChain`. A frozen track has it baked into its frozen audio and is not inverted again. Test [70] proves a track and its inverted copy sum to silence in the render, `processBlock` and the snapshot path.
- **A group's VCA offset is added to the fader and to a volume lane, in every path.** `faderGain` takes the offset (`-100` stays silence whatever it is): `mixTrackBlock` (`processBlock` and the snapshot path, from `PlaybackSnapshot::Track::vcaDb`) and `renderStems`' fader loop (plain through `trackGains`, automated per sample). `Editor::setGroupVca` is a plain step, so a VCA drag inside an `Editor::Gesture` is one undo step (tests [70], [59]).
- **Links reach the members of an active group; `alone` reaches the track only.** `Session::linkedTracksLocked` says who a change reaches (the group's own switch for gain, mute, solo or arm, and `active`). Gain moves every member by the same dB step, the step limited so that no member leaves `-100..+12`; mute, solo and arm set the same state on every member. `Session::setTrackArm` is the only arm setter (not undoable, as before); the window passes `alone` when Alt (Option) is held.
- **Colour, polarity and group are structure, undone by XML snapshots.** `Editor` changes them through `captureStructuralXml` and `recordStructural`, and publishes the playback snapshot first (`publishDirect`). Project XML: `colour` (hex text, absent when automatic), `polarity` and `group` on `<Track>`, and `<Groups><Group/></Groups>` under the project; an out-of-range group on load becomes -1 with a warning. `restoreEdit` leaves them alone.
- **The audio callback has its own copy of the transport** (`MainComponent::Source`: the position, the loop, the end of the audio, all atomics). `syncTransport` copies the loop and the end from the session; it is called by every change that moves them (`refreshNow`, the loop, the arrangement's `onStructure`), never by the 30 Hz timer (except when a plugin reports a new latency, which moves the end of the audio), because the callback's try-lock would otherwise miss a block now and then. A block is cut at the loop's end (`processBlock` is never called across it), and playing stops at the end of the audio unless the loop is on, a take is recording, or click-only free-run is active (`clickOnly`: `metronomeOn && endOfAudio <= 0`). `renderAudioBlock` runs the same code for the checks.
- **Every plugin is stereo, or it is refused.** `Session::configure` switches off every bus but the main pair (a sidechain), and `runsStereo` checks the result: a plugin that cannot take two channels in and out is refused on a track or the monitor chain with the reason (`makeSlot`), and a project or monitor chain that holds one keeps it as an unusable slot with its state. Each track's `scratch` is sized to its chain in `updateLatenciesLocked`; the monitor chain runs on a copy in `monitorScratch` of at least two channels.
- **Quit, NEW and OPEN wait while a render runs or a dialog is open** (`refuseWhileBusy`, `dialogOpen`: no second chooser replaces one; the action after a Save As chooser runs on the next message; test [28]).
- **Quit, NEW and OPEN with changes stop a running take first** (`askToDiscard` calls `stopRecording`, so the takes are clips and the project is dirty before the question). The question is Save / Don't save / Cancel (`askUnsaved`); Save on a project with no file runs the Save As chooser and the action goes on only once the file is written (tests [22], [23]).
- **Autosave never changes the project.** `autosaveNow` writes `Session::saveCopy` (the same XML, the name, file and dirty flag untouched) to `<name>.olympus.autosave` beside the project, or `autosave-untitled.olympus` beside `settings.xml`, through a temporary file that is then moved over the old one. A save deletes the project's (Save As the old one's too, `saveTo`); NEW deletes the session's own (`deleteAutosaves`); a discard that goes through (Quit via `dropAutosave`, an OPEN that succeeds) deletes what it dropped, and a failed open keeps it; the start offers a newer one (`offerRecovery`) and loads it with its project file kept (tests [24], [27]). The error of a failing autosave is shown once per failure streak (`autosaveFailing`). The timer calls it every `kAutosaveInterval` seconds; the checks call `autosaveNow()` directly.
- **The clipboard lives in the Editor, is not undoable state and is not in the project.** `Editor::copyClip`, `cutClip` and `pasteClip` hold one clip (its shared audio, place, gain, fades, mute and name) in a member; a cut and a paste are one undo step each, the clipboard survives undo and redo, NEW, OPEN and removing a track clear it (`clearClipboard`; it remembers the copy's track by number), and a paste is refused when the session's rate changed since the copy (the clip's audio is at the old rate).
- **Adding, removing, moving, or bypassing a track or a plugin (or replacing/copying a chain) is undoable.** `Editor` captures before/after project XML snapshots (`Session::toXml`/`Session::restoreEditXml`), preserving prior undo steps and calling `Editor::onBeforeStructureChange` (which closes track and master plugin windows) before restoring; `Editor::clearUndo()` is still called when starting a new project, opening a project, or adopting a new sample rate. Undo and redo still refuse a non-structural step recorded with another track count.
- **Clips are samples at the session's rate, and the session's rate is the device's.** `Session::adoptRate` (called by the window when a device starts, after a project opens or a new one starts, and when the monitor chain is read) sets it: an empty session only takes the rate; a session with audio resamples each pooled buffer once, scales its clips, markers and loop, and sets up every plugin and the monitor chain again. With no device running, the first imported file sets it. An imported file is resampled to it, and nothing is time-stretched: a tempo change moves the grid, not the audio. Overlapping clips on a track are layered when `Session::layered` is on (every new project, and a version 4 file that has the attribute): the clip with the higher `Clip::layer` (on a tie, the later index in the track) is opaque where it covers the clips under it, and those are silent there. At its two edges the upper clip and the lower one cross over with equal-power curves (`cos` on the lower clip, `sin` on the upper), over the crossfade length `crossfadeSamples` or the upper clip's own fade if that is longer, at most half the clip; where nothing lies under an edge, the edge keeps its linear fade. The cover and the edges are `Session::mixClipList` for the render, `processBlock` and the snapshot path alike. Off, and for a version 1 to 3 project (loaded with `layered` off), the clips are summed with their gain and fades, as before. A clip's gain line (`Clip::gainEnv`: points at SOURCE samples, linear in dB, held at the ends) multiplies in, so a trim or a split keeps it on the audio. A clip that no upper clip overlaps in the block and that has no gain line takes the sum's own code path. A clip whose file is missing keeps its place and plays silence (its `audio` is null). A version 1 project loads as one clip at 0.
- **The master applies to the mix only.** `masterDb` is applied to playback and to `mix.wav`; the stems are written without it (`renderStems`). Its range is -100 (silence) to +12 dB everywhere: the fader, `Editor::setMasterDb` and a project load (a saved value above +12 is set to +12 with a warning). The fader is set from the session only when it differs by more than 0.05 dB, and its tooltip shows the value (each track's fader tooltip shows its gain in dB too).
- **An external save of the open project file is noticed on the timer.** `MainComponent::checkExternalProjectChange` (every 15 ticks while not rendering, playing, recording or showing a dialog) compares `session.projectFile.getLastModificationTime()` with `loadedProjectMtime`: when the file on disk was modified outside the window (for example by `OlympusMcp`), a clean window reloads it at once (`openProject`), and a dirty window asks `askReload` (`Reload` / `Keep mine`, deleting the discarded autosave on reload and not re-prompting for the same mtime on keep; test [37]).
- **CLIP is latched per project: NEW and OPEN clear it** (`clearMasterClip`), as a click on the lamp does.
- **The device's output is held at full scale; the master's peak is read before that.** `Session::processBlock` measures `masterPeakL/R` before anything else reads the block; `DeviceCallback::deviceBlock` limits the device's outputs to [-1, 1] after the transport has filled them, sample by sample: NaN becomes 0 and an infinity the rail (not `FloatVectorOperations::clip`, which does not define NaN; no allocation, no lock; test [33]). Renders never pass there (`renderStems` keeps float, unclamped stems and mix). The timer is the one reader of the peaks (`updateMaster`, which exchanges them to 0): it latches CLIP at a sample of 1.0 or more (0 dBFS) until the lamp is clicked or a new or opened project starts, and holds the highest peak of the last two seconds for the read-out. An over therefore shows on CLIP although the device is protected (tests [29], [30]).
- Audio Units are hosted on macOS only (`JUCE_PLUGINHOST_AU`, set under `if(APPLE)`): the scan finds them through the system registry, so it loads each one to read it, under the dead-man's pedal. A VST3 and an AU of one name: the VST3 is kept.
- The scan reads plugins on the message thread and blocks it while it runs; a plugin that hangs in its read is caught only by the next run (the pedal). Say so wherever scanning is described.

- **Overriding lanes are not played, in any path.** `AutomationLane::overriding` is set while an automation pass writes the lane. `findActiveLane` skips it (the volume and pan of `processBlock`, `renderStems` and the snapshot path, so the fader and pan sound), and `runChain` skips a plugin lane (the parameter keeps the value set by hand). The flag is not saved, `restoreEdit` keeps it, the snapshot copies it, and `Editor::setAutomationOverriding` republishes the snapshot when it changes. The pass clears every flag it set when it stops, so a later render plays the lanes.
- **A pass is one undo step.** `AutomationWriter` opens an `Editor::Gesture` at its first write and closes it when the transport stops; a Write lane becomes Touch inside that gesture, so the step holds the mode change too. A structural edit during a pass drops the step (the gesture's own `gestureInvalid` rule): an accepted limit. A fader drag that starts before the first write is the outer gesture, so the step's label is then "Track gain". Undo and redo are refused while the pass is open.
- **The plugin listener only sets atomics.** `ParamTouchWatch` (one per slot, added to every parameter of the instance in `makeSlot` and in the retry of missing plugins, removed by `~Slot` before the instance goes) stores the parameter's index and whether its gesture starts. Its callbacks can come from any thread; only `AutomationWriter::tick` reads the two atomics, on the message thread.
- **The writer does nothing while a render runs.** `tick` returns at `renderRunning()` and try-locks `Session::lock`: a busy lock skips that tick. The begin and end calls from the faders and pans never wait for the lock.

## Not done yet (do not describe it as done)

- A track's plugins are not drawn on the arrangement: the FX button lists them (open, bypass, move, remove).
- No macOS CI job, and the app has not been run against the other twelve built plugins by a person; only Hermes was hosted by hand on Linux.
- No inline plugin parameter panel: a plugin is edited in its own window.
- Nothing has been listened to. Real-time playback of clips, the loop wrap and the metronome, the audio device, hosting a real third-party plugin and the plugin editors are checked only by the automated tests (the callback's own code, `renderAudioBlock`, `DeviceCallback::deviceBlock` with the checks' buffers), and a person must check them on the Mac. The real-plugin check (`OLYMPUS_PLUGIN_DIR`) has not been run on the clip engine.
- **MIDI input has never been played.** The keyboards, their MIDI threads and the AUDIO dialog's MIDI switches are not checked on a Mac: the checks give `handleIncomingMidiMessage` its events and time them with the blocks the fake device runs. A person must play a keyboard into a MIDI track, record and check the clip's place and its latency.
- **Recording has never run on a real interface.** No check opens a device: the take, its placement and its undo are checked with a fake device (`setDeviceForTest`) and fed blocks. Not checked: the AUDIO dialog (`AudioDeviceSelectorComponent`, a non-modal `DialogWindow`), the macOS microphone prompt (`MICROPHONE_PERMISSION_*` in CMake), a device's real latency values, a stop or change of the device under a real driver (its handling is the flag and `audioDeviceAboutToStart`), and the take files on a real disk under a long stall (six seconds of buffer, then dropped samples are counted by `Recorder::lost` and shown at stop as lost samples, and a file whose writes failed is named; neither has been seen on a real disk). Stopping a take on a stalled disk can freeze the window until the writer's buffer (up to about six seconds) is written, because `Recorder::stop` closes the writers on the message thread.
- A take's sub-lane shows its clip as a block, not its waveform, and a comp is not drawn in the sub-lanes (the main lane shows what plays). Recording again on a track adds another take group over the first, not a take of the same group.
- The arrangement's drags, menus and the look at other sizes are checked by its methods and one screenshot, not by a person's hand.
- **Monitoring has run only with a stand-in plugin** (`test::GainPlugin`). A real headphone correction plugin (a third-party VST3 or AU) has not been hosted in the chain, its editor not opened, its state not saved and read back, and nothing has been heard through it. The strip's buttons and menus are checked by the window's functions and one picture, not by a person's hand.
- The autosave timer itself is not checked (the checks call `autosaveNow()`); the save prompt's and the render's dialogs are only their defaults, which no check runs: the checks replace them, so a person must try them on the Mac.
- Automation passes are checked with the transport moved by the checks (`AutomationWriter::tick` with its own positions, and the window's fader drags), not with a playing transport on the Mac: a person must hear a Touch, Latch or Write pass there.
