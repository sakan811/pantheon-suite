# CLAUDE.md

Olympus Basic DAW: a JUCE standalone app (macOS, builds on Linux for CI) that holds a timeline of clips on tracks (with a tempo map, markers, a loop and undo), a chain of plugins on each track, and writes the stems out; plus an MCP server over the same
session so an agent can place the chains. See `README.md` for what it does; this file is what you need to change it safely. It is an **app**, so it lives in `apps/`; the dependency rule of the root CLAUDE.md
applies (`apps/*` -> `shared/*`, never a plugin or another app). It **hosts** plugins, but only at run time: it loads VST3 bundles (and Audio Units on macOS) that its scan finds, and links none of their code, so no dependency on `plugins/*` exists in
CMake. Third-party plugins are scanned at run time; that was decided by the user. The one place it knows about the suite's own plugins is `suiteNames()` in `Source/Catalog.h` (their product
names), which a test compares with every `plugins/*/CMakeLists.txt`, and which the "suite only" setting (`scanSuiteOnly`) keeps.

## Build and verify

```bash
scripts/build.sh olympus                 # OlympusTests + OlympusUiCheck, built and run
scripts/build.sh olympus snap            # docs/screenshot.png and docs/screenshot-record.png (the pictures the README embeds)
scripts/build.sh olympus app             # the window;  scripts/build.sh olympus OlympusMcp  # the server
OLYMPUS_PLUGIN_DIR=$PWD/plugins/hermes/build scripts/build.sh olympus tests     # also hosts a real built plugin (VST3)
```

- Definition of done: both checks pass, the screenshot is regenerated and looked at when the window changed, and the README's claims (tool count, targets, behaviour) still match. A change in `shared/ui` means building every plugin and app.
- `OlympusTests` and `OlympusUiCheck` need no built plugin and no audio device: plugins are `test::GainPlugin` (`Tests/TestPlugin.h`, a gain with two presets and an optional latency). Anything that touches the
  real hosting path (scan, load, state, render of an actual plugin) is the `OLYMPUS_PLUGIN_DIR` check: run it by hand after touching `Catalog.h` and say so.
- `UiCheck` runs headless with no display: it replaces `makeEditorWindow` so no native window is opened (a native window under a bare X server aborts the process). JUCE's `Button::triggerClick` acts asynchronously: use `press()` there.
- There is no listening test. Real-time playback, the audio device and the plugin editors in their own windows are checked by a person on the Mac; say so in the commit.

## Invariants

- **One Session, three users.** The window, the server and the tests all call `Session` (timeline edits through `Editor`, below); none keeps a copy of its state. Anything that changes tracks, clips or chains holds `Session::lock`; the audio callback only *tries* it (silence for that block if it cannot).
- **All tracks render together, block by block**, never one after another: Hestia's instances read each other through a bus in the plugin binary, so a track rendered alone would hear no neighbours. Keep it so.
- **A stem is aligned with its audio**: the chain's latency is taken off the front (and the run is longer by the longest latency); the real-time path delays the other tracks instead (`Track::delaySamples`). Test [4] and [5] pin both.
- **Stems are 32-bit float by default**, so they cannot clip and can be edited later; the mix is the sum of the written stems; a muted track (or one not soloed while another is) writes no stem. `RenderOptions::writeStems` off writes only `mix.wav`, which runs the tracks together exactly as a full render does (same bytes).
- **The message thread never waits for `Session::lock` while a render runs. Paint and `notes()` read the monitor latency with a try-lock (`monitorLatencyMs`, the value kept while busy), never `Session::monitorLatency`.** `renderStems` holds the lock for its whole run and sets `Session::renderBusy` (`renderRunning()`). `ArrangeView::snapshot` waits for the lock normally (the audio thread holds it for a moment each block) and returns its last model only when a render runs; the timer skips the latency update and the plugin-state check while a render runs. Any new timer or paint path follows the same rule (test [21]). A cancelled render closes and deletes the files of its own run and reports nothing (`RenderResult::stopped`); a render that fails after its files were made deletes them too (`discardRun`, test [20] proves the stems existed at the cancel). A render overwrites a same-named stem of an earlier render in that folder as soon as it starts (`makeWriter` deletes it first).
- **A project never loses what it cannot use.** A missing plugin stays as a slot with its saved state (`Slot::savedState`), a missing audio file keeps the track and its path; both are `warnings`, never errors. A project from a newer version is refused.
- **The project format is versioned** (`version` on `OlympusProject`); add attributes, never change what one means, and ignore what is unknown, as Orpheus' file does.
- **The server writes only what it is told to** (a project path, a render folder) and prints nothing but protocol on stdout. Every tool failure is an `isError` result with a reason an agent can act on; keep the 36 tools in `tools()` and in README in step.
- **The monitor chain is playback only, never in a render, not in the project, saved in `monitor.xml`**: `Session::processMonitor` runs after `processBlock` on the audio callback's playback block and nowhere else; `renderStems` and `processBlock` never touch it (test [31]), and it is not an undo step.
- **Recording is real-time safe, its files are written by a thread, and a take lands minus the latency**: `Recorder::push` allocates nothing, takes no lock and does no file IO (the `ThreadedWriter`s do, on a `TimeSliceThread`); `stop()` waits for a push in flight before it closes a file; `finishRecording` puts each take at `startSample - latencyCompensation`, or at 0 with the head before 0 skipped (`offset`), as one undo step. A take's disk problems are kept per take: `Recorder::Finished::lost` counts the frames the writer's FIFO refused (on the audio thread), and `failed` is set by `CheckedWriter`, which sits between the WAV writer and JUCE's `ThreadedWriter` (that one drops the result of its writes), when a write to the file fails on the writer thread. `stopRecording` reports both: the lost samples with their length in ms (dropped frames are not written, so the take is shorter by that much and what follows the loss sits that much early; nothing is padded; with several takes that lost samples, the largest is named with its track and the others are listed); a file that failed keeps what it holds. `finishRecording` skips a take it cannot place and places the rest; the first reason is reported (test [41]).
- **One audio path, the device's.** `MainComponent::DeviceCallback::deviceBlock` is what the device calls and what the checks call with their own buffers: the inputs go to `Recorder::push` first (always, so the meters work), then `Source::getNextAudioBlock` fills the outputs (it clears them first, so unused outputs are silent). `processMonitor` runs on the playback block after `processBlock`, as its invariant says. A device with no outputs plays nothing, but its transport still advances (into a scratch buffer) and its takes still get their inputs. `audioDeviceAboutToStart` (before the callbacks start; marshalled to the message thread if it comes from another) ends a running take, because a take cannot go on across a new rate or block size, prepares the recorder and the transport's scratch, and adopts the device's rate; `audioDeviceStopped` (device thread) only sets a flag that the timer reads and ends the take.
- **Takes name device inputs by their absolute number; the callback passes only the switched-on ones.** The device hands `deviceBlock` its active inputs in order, so `Recorder::prepare` maps each absolute input to its position (`position`, -1 when it is off). A take or a meter on an input that is off is silence, and REC refuses that take with the track and the input named. `inputChoices` offers only the inputs that are on.
- **A take starts where the playhead was at its first block.** `deviceBlock` sets `Source::recordStart` from the position at the first block `Recorder::push` writes (push returns that decision, so the start and the write are one decision); REC clears it first. `stopRecording` places each take at `recordStart - latency`, with the latency fixed at REC (device input + output latency + `extraLatencySamples` + `Session::monitorLatency()` + `Session::maxLatency()`, the longest track chain the tracks are delayed by). While a take runs the loop does not wrap, the end of the audio does not stop it, `seek` is refused (the take is one continuous recording), and a track cannot be removed.
- **Plugins are created and edited on the message thread.** The window and the server run on it. `chooseAndRender` closes the tracks' plugin windows and stops the transport on the message thread before its progress window's worker starts; the worker then runs `Session::renderStems`, whose `OfflineScope` also prepares the plugins on that thread (a known issue in DAW-ROADMAP.md, not yet fixed; the invariant does not hold there).
- **A start that died is not repeated.** The monitor chain and the last project are loaded between two pedal files (`monitor-load.pedal`, `project-load.pedal`, Settings.h): a pedal found at start is removed and that load is skipped, the file is left untouched, and a note says so. `loadSkippedMonitorChain` (PLUGINS) reads the chain again with the pedal around it.
- **A plugin's latency change is followed on the window's timer.** Its listener (`LatencyWatch`, one per session, removed by each slot before its instance goes) only sets a flag; the timer calls `updateLatencies`. The MCP server has no timer and does not follow it.
- **Everything is drawn from the kit** (`shared/ui`): `LampButton` exists only because the kit's look-and-feel lights every switch in one colour; if the kit grows per-button colours, use them and delete it. The window is 16:10 (`kDesignWidth` a multiple of 8).
- **Adding a plugin to the suite** means adding its product name to `suiteNames()` (a test fails until you do).
- **Every timeline edit goes through `Editor`** (`Source/Edit.h`): clips, track gain, pan, mute, solo and name, the master, tempo, time signature, loop, metronome, markers, snap and grid. It takes the session lock, refuses a bad argument with a reason and changes nothing, and pushes one undo step per change; a `Gesture` makes a drag one step. Snap and grid are saved but not undone. Nothing else writes those fields: the window, the arrangement and the server all call `Editor`.
- **The audio callback has its own copy of the transport** (`MainComponent::Source`: the position, the loop, the end of the audio, all atomics). `syncTransport` copies the loop and the end from the session; it is called by every change that moves them (`refreshNow`, the loop, the arrangement's `onStructure`), never by the 30 Hz timer (except when a plugin reports a new latency, which moves the end of the audio), because the callback's try-lock would otherwise miss a block now and then. A block is cut at the loop's end (`processBlock` is never called across it), and playing stops at the end of the audio unless the loop is on. `renderAudioBlock` runs the same code for the checks.
- **Every plugin is stereo, or it is refused.** `Session::configure` switches off every bus but the main pair (a sidechain), and `runsStereo` checks the result: a plugin that cannot take two channels in and out is refused on a track or the monitor chain with the reason (`makeSlot`), and a project or monitor chain that holds one keeps it as an unusable slot with its state. Each track's `scratch` is sized to its chain in `updateLatenciesLocked`; the monitor chain runs on a copy in `monitorScratch` of at least two channels.
- **Quit, NEW and OPEN wait while a render runs or a dialog is open** (`refuseWhileBusy`, `dialogOpen`: no second chooser replaces one; the action after a Save As chooser runs on the next message; test [28]).
- **Quit, NEW and OPEN with changes stop a running take first** (`askToDiscard` calls `stopRecording`, so the takes are clips and the project is dirty before the question). The question is Save / Don't save / Cancel (`askUnsaved`); Save on a project with no file runs the Save As chooser and the action goes on only once the file is written (tests [22], [23]).
- **Autosave never changes the project.** `autosaveNow` writes `Session::saveCopy` (the same XML, the name, file and dirty flag untouched) to `<name>.olympus.autosave` beside the project, or `autosave-untitled.olympus` beside `settings.xml`, through a temporary file that is then moved over the old one. A save deletes the project's (Save As the old one's too, `saveTo`); NEW deletes the session's own (`deleteAutosaves`); a discard that goes through (Quit via `dropAutosave`, an OPEN that succeeds) deletes what it dropped, and a failed open keeps it; the start offers a newer one (`offerRecovery`) and loads it with its project file kept (tests [24], [27]). The error of a failing autosave is shown once per failure streak (`autosaveFailing`). The timer calls it every `kAutosaveInterval` seconds; the checks call `autosaveNow()` directly.
- **The clipboard lives in the Editor, is not undoable state and is not in the project.** `Editor::copyClip`, `cutClip` and `pasteClip` hold one clip (its shared audio, place, gain, fades, mute and name) in a member; a cut and a paste are one undo step each, the clipboard survives undo and redo, NEW, OPEN and removing a track clear it (`clearClipboard`; it remembers the copy's track by number), and a paste is refused when the session's rate changed since the copy (the clip's audio is at the old rate).
- **Adding or removing a track or a plugin is not undoable.** It is not an `Editor` step: the window and the server call `Editor::clearUndo()` after it (the server after add/remove track, add/remove plugin, set_chain and copy_chain), and after opening or starting a project. Undo and redo also refuse a step recorded with another track count.
- **Clips are samples at the session's rate, and the session's rate is the device's.** `Session::adoptRate` (called by the window when a device starts, after a project opens or a new one starts, and when the monitor chain is read) sets it: an empty session only takes the rate; a session with audio resamples each pooled buffer once, scales its clips, markers and loop, and sets up every plugin and the monitor chain again. With no device running, the first imported file sets it. An imported file is resampled to it, and nothing is time-stretched: a tempo change moves the grid, not the audio. Overlapping clips on a track are summed, with their gain and fades. A clip whose file is missing keeps its place and plays silence (its `audio` is null). A version 1 project loads as one clip at 0.
- **The master applies to the mix only.** `masterDb` is applied to playback and to `mix.wav`; the stems are written without it (`renderStems`). Its range is -100 (silence) to +12 dB everywhere: the fader, `Editor::setMasterDb` and a project load (a saved value above +12 is set to +12 with a warning). The fader is set from the session only when it differs by more than 0.05 dB, and its tooltip shows the value.
- **CLIP is latched per project: NEW and OPEN clear it** (`clearMasterClip`), as a click on the lamp does.
- **The device's output is held at full scale; the master's peak is read before that.** `Session::processBlock` measures `masterPeakL/R` before anything else reads the block; `DeviceCallback::deviceBlock` limits the device's outputs to [-1, 1] after the transport has filled them, sample by sample: NaN becomes 0 and an infinity the rail (not `FloatVectorOperations::clip`, which does not define NaN; no allocation, no lock; test [33]). Renders never pass there (`renderStems` keeps float, unclamped stems and mix). The timer is the one reader of the peaks (`updateMaster`, which exchanges them to 0): it latches CLIP at a sample of 1.0 or more (0 dBFS) until the lamp is clicked or a new or opened project starts, and holds the highest peak of the last two seconds for the read-out. An over therefore shows on CLIP although the device is protected (tests [29], [30]).
- Audio Units are hosted on macOS only (`JUCE_PLUGINHOST_AU`, set under `if(APPLE)`): the scan finds them through the system registry, so it loads each one to read it, under the dead-man's pedal. A VST3 and an AU of one name: the VST3 is kept.
- The scan reads plugins on the message thread and blocks it while it runs; a plugin that hangs in its read is caught only by the next run (the pedal). Say so wherever scanning is described.

## Not done yet (do not describe it as done)

- No multi-select: one clip is selected at a time, so copy, cut and paste work on one clip.
- No mixer view (roadmap step 2). The fader and pan of a track are in the arrangement's header only.
- A track's plugins are not drawn on the arrangement: the FX button lists them (open, bypass, move, remove).
- No macOS CI job, and the app has not been run against the other twelve built plugins by a person; only Hermes was hosted by hand on Linux.
- No inline plugin parameter panel: a plugin is edited in its own window.
- No per-slot wet/dry.
- Nothing has been listened to. Real-time playback of clips, the loop wrap and the metronome, the audio device, hosting a real third-party plugin and the plugin editors are checked only by the automated tests (the callback's own code, `renderAudioBlock`, `DeviceCallback::deviceBlock` with the checks' buffers), and a person must check them on the Mac. The real-plugin check (`OLYMPUS_PLUGIN_DIR`) has not been run on the clip engine.
- **Recording has never run on a real interface.** No check opens a device: the take, its placement and its undo are checked with a fake device (`setDeviceForTest`) and fed blocks. Not checked: the AUDIO dialog (`AudioDeviceSelectorComponent`, a non-modal `DialogWindow`), the macOS microphone prompt (`MICROPHONE_PERMISSION_*` in CMake), a device's real latency values, a stop or change of the device under a real driver (its handling is the flag and `audioDeviceAboutToStart`), and the take files on a real disk under a long stall (six seconds of buffer, then dropped samples are counted by `Recorder::lost` and shown at stop as lost samples, and a file whose writes failed is named; neither has been seen on a real disk). Stopping a take on a stalled disk can freeze the window until the writer's buffer (up to about six seconds) is written, because `Recorder::stop` closes the writers on the message thread.
- No software input monitoring (use the interface's direct monitoring), no punch-in or loop recording, no comping of takes, no take lanes: a take is a clip, and recording again on a track adds another clip over the first.
- The arrangement's drags, menus and the look at other sizes are checked by its methods and one screenshot, not by a person's hand.
- **Monitoring has run only with a stand-in plugin** (`test::GainPlugin`). A real headphone correction plugin (a third-party VST3 or AU) has not been hosted in the chain, its editor not opened, its state not saved and read back, and nothing has been heard through it. The strip's buttons and menus are checked by the window's functions and one picture, not by a person's hand.
- The autosave timer itself is not checked (the checks call `autosaveNow()`); the save prompt's and the render's dialogs are only their defaults, which no check runs: the checks replace them, so a person must try them on the Mac.
- The add-plugin list of the monitor chain has no search box: over 25 plugins it is grouped into one sub-menu per maker, which a long list of makers still makes long.
